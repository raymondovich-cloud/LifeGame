# Health Index 1.0 — методология

**Статус:** BASELINE / PLANNED
**Версия модели:** 1.0
**Дата:** 08.10.2026

## 1. Назначение

Health Index — производный показатель LifeGame для оценки устойчивости повседневной системы здоровья и восстановления. Он не является медицинским диагнозом, клиническим инструментом или заменой врача.

Цель индекса — ответить на прикладной вопрос: **насколько устойчиво пользователь поддерживает сон, физическую активность, тренировочный режим, питание и образ жизни в наблюдаемом периоде?**

Модель строится так:

`RAW DATA → METRICS → FACTORS → HEALTH INDEX → DIAGNOSIS → RECOMMENDATION`

## 2. Шкала

Итоговый индекс: **0–100**.

- 90–100 — Excellent
- 75–89 — Good
- 60–74 — Attention
- 40–59 — Weak
- 0–39 — Critical

Границы являются продуктовой шкалой, а не медицинскими порогами.

## 3. Факторы и веса

| Фактор | Вес |
|---|---:|
| Recovery / Восстановление | 25% |
| Activity / Повседневная активность | 20% |
| Training / Тренировочная система | 15% |
| Nutrition / Питание | 15% |
| Lifestyle / Образ жизни | 15% |
| Body / Параметры тела | 10% |

Сумма весов = 100%.

Recovery получает максимальный вес, поскольку хронический дефицит восстановления способен ухудшать устойчивость остальных поведенческих факторов. Body получает минимальный прямой вес: масса, рост и другие физиологические показатели не должны автоматически доминировать над поведением пользователя.

## 4. Расчёт фактора

Каждый фактор состоит из нормализованных метрик со значениями от 0 до 100.

Для фактора `f`:

`F_f = Σ(w_i × m_i) / Σ(w_i)`

где `m_i` — нормализованный балл метрики, а `w_i` — её вес внутри фактора.

Нормализация выполняется относительно **target bands** — целевых диапазонов, заданных отдельным профилем методологии. Целевой диапазон не должен автоматически трактоваться как медицинская норма.

Для метрик, где «больше» не всегда лучше, применяется piecewise-функция:

`m(x) = 100`, если x находится в целевом диапазоне;

`m(x) = 100 × d(x)`, если x находится за пределами диапазона, где `d(x)` уменьшается плавно до 0.

Конкретные target bands должны пройти отдельную валидацию перед переводом модели в IMPLEMENTED.

## 5. Состав факторов

### Recovery — 25%

Базовые метрики:
- продолжительность сна;
- регулярность сна;
- время сна/подъёма;
- субъективное качество восстановления;
- resting heart rate — только при наличии достаточной серии наблюдений;
- HRV — только при наличии корректного источника и валидированной методики.

Не следует считать HRV или resting heart rate самостоятельным диагнозом.

### Activity — 20%

Базовые метрики:
- шаги;
- расстояние;
- активные калории;
- минуты активности.

При автоматическом источнике данные агрегируются за день и затем за окно оценки.

### Training — 15%

Базовые метрики:
- количество тренировок;
- длительность;
- регулярность;
- тип нагрузки;
- баланс нагрузки и восстановления.

Одна тяжёлая тренировка не должна сама по себе резко снижать индекс. Оценивается устойчивость системы во времени.

### Nutrition — 15%

На первом этапе:
- регулярность питания;
- наличие пользовательского режима питания;
- субъективная оценка качества питания;
- вода.

Калории и макронутриенты не должны автоматически использоваться без надёжного источника данных.

### Lifestyle — 15%

Базовые метрики:
- алкоголь;
- курение;
- никотин;
- стресс;
- настроение;
- субъективное самочувствие.

Объективные и субъективные данные хранятся и рассчитываются раздельно до стадии нормализации.

### Body — 10%

Контекстные метрики:
- вес;
- рост;
- BMI как производная метрика;
- resting heart rate;
- артериальное давление — при ручном вводе.

Body не используется для медицинской диагностики. BMI и давление требуют отдельной интерпретации и не должны напрямую превращаться в утверждения о наличии заболевания.

## 6. Окно расчёта

Основное окно Health Index: **28 дней**.

Для метрик с высокой частотой наблюдений используется агрегирование внутри 28-дневного окна. Для медленно меняющихся параметров применяется последнее валидное значение с ограничением срока актуальности.

Дополнительное диагностическое окно: **7 дней** — для выявления краткосрочных изменений.

Долгосрочная динамика: **90 дней** — только для трендов, а не как обязательная база текущего индекса.

## 7. Пропущенные данные

Отсутствие данных не считается плохим здоровьем.

Для доступных факторов используется renormalization:

`H = Σ(W_f × F_f) / Σ(W_f_available)`

где `W_f_available` — веса факторов, по которым есть достаточные данные.

Одновременно рассчитывается `Data Coverage` — доля доступного веса модели.

Правило интерпретации:
- `<40%` — индекс не считается достоверным и должен отображаться как **Insufficient data**;
- `40–69%` — **Preliminary**;
- `≥70%` — **Full**.

Таким образом новый пользователь не получает искусственно низкий индекс из-за пустых полей.

## 8. Доверие к данным

Помимо Health Index рассчитывается `Data Confidence`.

Confidence зависит от:
- полноты данных;
- регулярности измерений;
- давности данных;
- надёжности источника.

Ручной ввод не запрещается и не приравнивается автоматически к плохому источнику. Однако автоматически полученные последовательные данные могут иметь более высокую надёжность для метрик, которые устройство действительно измеряет.

Confidence не изменяет сам индекс. Он определяет, насколько уверенно система должна его интерпретировать и показывать пользователю.

## 9. Recency weighting

Внутри 28-дневного окна новые наблюдения имеют больший вес, чем старые.

Для наблюдения возраста `d` дней используется:

`r(d) = exp(-λd)`

где `λ` выбирается отдельно для класса метрики и должен быть зафиксирован до реализации.

Это позволяет индексу реагировать на реальные изменения, не превращая один хороший или плохой день в резкий скачок.

## 10. Защита от двойного счёта

Одна физиологическая характеристика не должна одновременно многократно влиять на индекс без обоснования.

Например:
- resting heart rate может участвовать в Recovery;
- тот же показатель в Body используется только как контекст либо с нулевым весом при наличии Recovery-оценки.

То же правило применяется к другим производным метрикам.

## 11. Диагностика

Health Index должен объяснять не только **сколько**, но и **почему**.

После расчёта строится профиль факторов:

`Recovery = 54`
`Activity = 82`
`Training = 71`
`Nutrition = 63`
`Lifestyle = 88`
`Body = 76`

Главным ограничителем считается фактор с наибольшим отрицательным вкладом относительно целевого уровня, а не просто фактор с минимальным абсолютным значением.

Диагностика должна отвечать в формате:

**Основной фактор:** Recovery

**Что влияет:** нерегулярный сон и недостаточное восстановление.

**Изменение:** Recovery снизился на X пунктов за 7 дней.

**Приоритет действия:** восстановить регулярность сна.

Нельзя выдавать медицинские диагнозы, причинно-следственные утверждения без достаточных данных или рекомендации, которые требуют клинической оценки.

## 12. Защита от резких скачков

Изменение итогового индекса между последовательными расчётами должно быть ограничено механизмом smoothing.

Рабочая модель:

`H_final = α × H_current + (1 − α) × H_previous`

где `α` определяется качеством и свежестью данных.

Для первого релиза конкретные значения `α` и максимального суточного изменения должны быть отдельно валидированы на тестовых сценариях.

## 13. Что не входит в Health Index напрямую

Следующие данные могут собираться для контекста, но не должны автоматически влиять на индекс:
- температура;
- отдельные медицинские события;
- диагнозы;
- лекарства;
- лабораторные показатели;
- единичные аномальные измерения без проверки качества данных.

Их наличие не превращает LifeGame в медицинскую систему.

## 14. Источники данных

Этап 1: ручной ввод.

Этап 2: автоматизация доступных метрик через Apple Health / HealthKit и другие разрешённые источники.

Источник должен передавать происхождение значения и время измерения. Application слой преобразует raw data в нормализованные метрики; Index работает только с разрешённым контрактом данных.

## 15. Архитектурная граница

Health Index не хранит пользовательские данные.

Направление:

`Health Domain → Application → Health Index → Diagnosis → Presentation`

Index получает только необходимые нормализованные данные и возвращает:
- итоговый score;
- factor scores;
- coverage;
- confidence;
- diagnostic signals;
- methodology metadata.

Persistence, authentication, UI и HealthKit не должны попадать внутрь расчётного слоя.

## 16. Статус модели

**BASELINE / PLANNED.**

Архитектурная схема и состав факторов согласованы как основа Health 1.0.

До статуса IMPLEMENTED необходимо отдельно валидировать:
1. target bands;
2. внутренние веса метрик;
3. коэффициенты recency;
4. smoothing;
5. тестовые сценарии и пограничные случаи;
6. формулировки пользовательской диагностики.

После этой валидации модель может быть реализована в `source/index/health/` без переноса бизнес-логики в Presentation.
