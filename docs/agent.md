# LifeGame — Agent Rules

## 1. Чистая архитектура

Первостепенное правило проекта — соблюдать принцип **Clean Architecture (Чистая архитектура)**.

Бизнес-логика и правила предметной области должны быть изолированы от технических деталей, инфраструктуры, UI, платформ и способов хранения данных.

При разработке новых функций необходимо в первую очередь определить, к какому архитектурному слою относится ответственность, и не допускать нарушения границ между слоями.

## 2. Один файл = одна ответственность

Каждый файл проекта должен иметь **одну чётко определённую ответственность**.

Не следует объединять в одном файле:
- несколько независимых бизнес-задач;
- разные архитектурные слои;
- UI, бизнес-логику и инфраструктурный код;
- несвязанные функции только ради сокращения количества файлов.

Если ответственность становится слишком большой или неоднозначной — её необходимо разделить на отдельные модули.

## 3. Строчные имена файлов и папок

Все новые и изменяемые **папки и файлы проекта должны называться со строчной буквы**.

Правила:
- первая буква имени файла — строчная;
- первая буква имени папки — строчная;
- не создавать новые имена с заглавной первой буквой;
- числовые имена директорий с датой, например `1.10.2026`, не подпадают под это правило;
- при создании вложенных директорий это правило применяется на каждом уровне;
- имена должны оставаться единообразными во всём проекте.

Примеры:

Правильно:
- `docs`
- `changes`
- `finance.js`
- `agent.md`
- `user.memory.js`

Неправильно:
- `Docs`
- `Changes`
- `Finance.js`
- `Agent.md`

Это правило относится ко всем новым файлам и папкам, которые мы создаём, сохраняем или редактируем в рамках проекта.

## 4. Версионирование каждого изменения файла

При **каждом создании, изменении или редактировании файла** в самом начале его кода должна быть указана текущая версия изменения.

Формат:

`finance.js — Version 1.0`

При следующем изменении:

`finance.js — Version 1.1`

Далее версия увеличивается последовательно:

`1.2`, `1.3`, `1.4` и т.д.

Правила:
- версия относится непосредственно к конкретному файлу;
- при первом создании файла используется `1.0`;
- каждое последующее изменение этого файла увеличивает номер версии на `0.1`;
- строка версии должна находиться **в самом начале кода файла**;
- версия должна обновляться при любом изменении содержимого файла, даже если изменение небольшое.

Для файлов, где синтаксис не поддерживает обычный комментарий в первой строке, используется первый допустимый для данного формата способ указать версию.

## 5. Журнал изменений

Для каждого пользовательского запроса, в результате которого изменяется репозиторий, создаётся **один Change-файл**.

Количество изменённых файлов внутри запроса не влияет на количество Change-файлов:
- один запрос → один Change-файл;
- три изменённых файла в одном запросе → один Change-файл;
- три отдельных запроса → три Change-файла.

### Расположение Change-файлов

Change-файлы разрешено хранить **только** внутри папки закреплённого дня рабочей сессии:

`docs/changes/D.M.YYYY/`

Например:

`docs/changes/1.10.2026/07-15-10.md`

Change-файлы запрещено размещать:
- непосредственно в `docs/changes/`;
- в папке другого дня рабочей сессии;
- в любых иных директориях.

### Закреплённый день рабочей сессии

В начале рабочей сессии определяется её закреплённый день.

Все Change-файлы, созданные в рамках этой рабочей сессии, хранятся в папке этого дня, даже если фактическая календарная дата после полуночи уже изменилась.

Переход через 00:00 **не создаёт новую папку**, пока продолжается та же рабочая сессия.

### Имя Change-файла

Имя Change-файла содержит только фактическое время его создания:

`HH-MM-SS.md`

Например:

`docs/changes/1.10.2026/07-15-10.md`

**Истиной для времени Change-файла является фактическое время его создания.**

### Содержание Change-файла

Каждый Change-файл должен содержать:
- дату и точное фактическое время создания;
- `MSK (UTC+03:00)`;
- пользовательский запрос, к которому относится запись;
- изменённые файлы;
- версии изменённых файлов до и после изменения;
- что именно было изменено;
- причину изменения;
- важные архитектурные решения, если они были приняты;
- итоговый статус изменения.

### Язык Change-файлов

**Каждый новый файл в `docs/changes/` должен быть написан полностью на русском языке.**

Допускается использовать технические термины, названия файлов, классов, функций, директорий, команд, технологий и другие идентификаторы в их оригинальном написании.

### Исключения для Change-файлов

Change-файлы являются историческими записями и не участвуют в обычном версионировании файлов проекта.

Редактирование существующего Change-файла **не создаёт новый Change-файл**, если пользователь отдельно не указал необходимость зафиксировать это редактирование новым Change.

Change-файл также не создаёт рекурсивный Change при собственном создании.

Журнал изменений является частью документации проекта и используется для восстановления контекста, аудита и продолжения разработки.

## 6. Двухэтапный процесс разработки

Любой запрос пользователя, который предполагает **изменение репозитория**, должен проходить два отдельных этапа.

### Этап 1 — Обсуждение и согласование

До внесения изменений в GitHub необходимо:

1. понять, что именно требуется изменить;
2. проверить применимые правила и архитектуру проекта;
3. определить затрагиваемые файлы и архитектурные слои;
4. выявить неоднозначности и задать необходимые уточняющие вопросы;
5. если существует несколько разумных вариантов реализации — представить их пользователю;
6. кратко описать последствия и архитектурные особенности вариантов;
7. получить явное решение пользователя о выбранном варианте.

**На этом этапе изменения в репозиторий не вносятся.**

### Этап 2 — Реализация

После явного подтверждения пользователя выбранного решения необходимо:

1. проверить актуальное состояние репозитория;
2. повторно свериться с `docs/agent.md`;
3. реализовать согласованный вариант;
4. изменить только необходимые файлы;
5. соблюдать Clean Architecture, DDD и принцип «один файл = одна ответственность»;
6. обновить версии всех изменённых файлов;
7. создать запись в `docs/changes/`;
8. проверить имена новых и изменённых файлов и папок;
9. зафиксировать результат в Git;
10. сообщить пользователю, что именно было изменено, какие файлы затронуты и каким commit это зафиксировано.

### Исключение

Если пользователь явно просит выполнить конкретное изменение **без предварительного обсуждения**, реализация может быть выполнена сразу.

При этом правила архитектуры, версионирования, lowercase naming и Change Log остаются обязательными.

## 7. Единая система дизайна

**`design` — это не один огромный `design.js`, а Design System из маленьких независимых модулей. Каждый файл отвечает только за одну категорию визуальных правил.**

Design System является единым источником визуальных правил приложения и должен обеспечивать единый дизайн во всех доменах и интерфейсах LifeGame.

### 7.1. Технология Design System

Для веб-версии LifeGame визуальный слой Design System реализуется на **CSS**.

JavaScript не является частью `source/design` и не используется для хранения визуальных правил.

JavaScript может использоваться в UI/Application-слое только для поведения интерфейса, например для переключения темы через атрибут `data-theme`, но не для дублирования CSS-правил.

### 7.2. Утверждённая структура `source/design`

Структура Design System является фиксированной архитектурной основой.

Изменение этой структуры допускается только после отдельного обсуждения и явного согласования. После согласования структура может быть отредактирована.

    │   ├── typography.css
    │   ├── spacing.css

    │   ├── shadows.css
    │   ├── borders.css
    │   ├── gradients.css
    │   └── motion.css
    │
    ├── foundation/
    │   ├── reset.css
    │   ├── base.css
    │   ├── layout.css
    │   └── accessibility.css
    │
    ├── components/
    │   ├── button.css
    │   ├── card.css
    │   ├── input.css
    │   ├── modal.css
    │   ├── accordion.css
    │   ├── navigation.css
    │   ├── header.css
    │   ├── list.css

### 7.3. Ответственность каталогов

`tokens/` — атомарные визуальные значения Design System: цвета, типографика, интервалы, радиусы, тени, границы, градиенты и motion-правила.

`foundation/` — базовые правила интерфейса: reset, глобальные стили, базовая типографика, layout и accessibility.

`components/` — переиспользуемые UI-компоненты. Каждый файл отвечает за внешний вид одной категории компонента.

`patterns/` — составные визуальные паттерны, построенные из Design System components. Они не содержат бизнес-логику.

`themes/` — визуальные темы приложения. Темы переопределяют Design Tokens через CSS Custom Properties.

`design.css` — единая точка входа Design System. Файл подключает модули Design System и не должен превращаться в монолитный файл со всеми стилями. Если отдельная ответственность требует собственного модуля, создаётся отдельный файл.

### 7.4. Архитектурные ограничения Design System

Не создавать внутри `source/design`:
- `design.js`;
- `theme.js`;
- `colors.js`;
- JS-файлы визуальных компонентов;
- бизнес-логику;
- расчёты Finance, Health, Development или других доменов;
- прямые зависимости от `domain`, `memory` или `infrastructure`.

Не создавать отдельные доменные стили вида `finance.css`, `health.css` или `development.css` внутри Design System без отдельного архитектурного согласования. Домены используют общую Design System.

Design System должна оставаться независимой от бизнес-доменов.

При создании новых элементов интерфейса необходимо сначала проверить, существует ли соответствующий компонент или токен в Design System. Если существует — его необходимо переиспользовать, а не создавать отдельную локальную реализацию.

## Правило для дальнейшей разработки

Перед созданием или изменением кода необходимо сверяться с этим документом.

Если предлагаемое решение нарушает эти правила, архитектура должна быть пересмотрена до написания кода.

После каждого изменения необходимо:
1. проверить имена новых и изменяемых файлов и папок;
2. обновить версию изменённого файла;
3. создать один Change-файл для текущего пользовательского запроса;
4. указать фактическую дату и точное время создания Change;
5. зафиксировать результат изменения в Git.

Для самого Change-файла правила версионирования и создания рекурсивного Change не применяются.


## 8. Утверждённый визуальный референс интерфейса

Ниже закреплён визуальный референс, на основе которого далее разрабатывается интерфейс LifeGame:

![LifeGame — утверждённый визуальный референс](../admin.sistem/docs/52BD4129-4F9E-4E68-A1BC-9ECAB1F40606.png)

Этот референс является исходной точкой для визуального слоя проекта.

### 8.1. Основные визуальные принципы

При дальнейшей разработке необходимо сохранять следующие характеристики референса:

- преимущественно чёрный фон и тёмная визуальная среда;
- минималистичная композиция без визуального шума;
- высокий контраст между основным текстом и второстепенной информацией;
- крупная, выразительная типографика для названий модулей;
- небольшие uppercase-метки для системной информации;
- тонкие светлые границы и мягкие скругления карточек;
- сдержанные градиенты, глубина и мягкие свечения без перегрузки интерфейса;
- ощущение премиального системного интерфейса;
- модульная структура экрана;
- нижняя навигация с чётким выделением активного модуля;
- визуальное разделение основной информации, системного статуса и навигации;
- единый визуальный язык для Finance, Health и Development.

### 8.2. Статус референса

Референс **утверждён как текущая визуальная база проекта**, но не является неизменяемым макетом.

В процессе разработки отдельные параметры — цвета, размеры, интервалы, типографика, радиусы, эффекты и композиция — могут быть изменены только при необходимости и после согласования.

При расхождении между существующим кодом Design System и этим референсом сначала необходимо определить, является ли расхождение сознательным архитектурным решением или незапланированным отклонением.

Не копировать визуальные значения непосредственно в доменные файлы. Все повторно используемые визуальные параметры должны находиться в `source/design` в соответствии со структурой Design System.


## 9. Архитектурная модель и правила зависимостей

### 9.1. Архитектурная структура

LifeGame 3.0 использует шесть архитектурных уровней и одну независимую Design System.

```
source/
│
├── core/
├── domain/
├── application/
├── presentation/
├── infrastructure/
├── memory/
└── design/
```

### Шесть архитектурных уровней

1. `core/`
2. `domain/`
3. `application/`
4. `presentation/`
5. `infrastructure/`
6. `memory/`

### Отдельная система

7. `design/`

`design/` является Design System LifeGame.

`design/` НЕ является архитектурным уровнем и не входит в иерархию бизнес-зависимостей.

### 9.2. Основной принцип зависимостей

Зависимость всегда направлена внутрь архитектуры — к более стабильным и абстрактным слоям.

```
ВНЕШНИЙ УРОВЕНЬ
       ↓
PRESENTATION
       ↓
APPLICATION
       ↓
DOMAIN
       ↓
CORE
```

Внешний уровень может знать о внутреннем.

Внутренний уровень НЕ должен знать о внешнем.

Направление зависимости запрещено разворачивать в обратную сторону ради удобства текущей реализации.

Новая зависимость НЕ может создаваться только потому, что она сейчас удобна.

Если появляется необходимость в новой зависимости, сначала необходимо проверить архитектурную границу и при необходимости официально изменить архитектурный контракт. Только после этого допускается реализация.

### 9.3. Изоляция Domain

`domain/` содержит бизнес-логику и бизнес-правила LifeGame.

Domain НЕ должен напрямую зависеть от:

- `presentation`;
- UI;
- DOM;
- Browser API;
- `infrastructure`;
- хранилищ;
- конкретных баз данных;
- внешних SDK;
- `memory`;
- конкретных реализаций шифрования;
- `design`.

Domain НЕ должен знать о технических деталях системы.

### 9.4. Изоляция Domain-модулей

Domain-модули НЕ должны напрямую зависеть друг от друга.

Например:

```
domain/finance
      X
      X
domain/health
```

Ни один модуль не должен напрямую импортировать внутреннюю реализацию другого Domain-модуля.

Если модулям необходимо взаимодействовать, взаимодействие осуществляется через определённый контракт, событие или механизм координации Application.

### 9.5. Граница Memory

`domain/` НЕ имеет права напрямую импортировать или использовать `memory/`.

Запрещено:

```
domain
   ↓
memory
```

Допустимый путь:

```
domain
   ↓
событие / контракт
   ↓
механизм событий / граница Application
   ↓
Memory Adapter
   ↓
memory
```

Memory отвечает за хранение и работу с историческим или системным состоянием в рамках определённых для неё контрактов.

### 9.6. Application

`application/` отвечает за координацию сценариев использования системы и взаимодействие между бизнес-возможностями.

Application может зависеть от:

- Domain;
- разрешённых контрактов Core;
- разрешённых абстракций.

Application НЕ должен становиться заменой Domain.

Бизнес-правила находятся в `domain/`, а не в `application/`.

### 9.7. Presentation

`presentation/` отвечает за отображение состояния приложения и обработку пользовательского взаимодействия.

Допустимое направление:

```
presentation
      ↓
application
```

Presentation НЕ должен:

- содержать бизнес-правила;
- напрямую изменять данные в хранилище;
- напрямую обращаться к базе данных;
- напрямую обращаться к Memory;
- напрямую использовать конкретные реализации Infrastructure;
- содержать реализацию шифрования;
- обходить Application для изменения состояния Domain.

### 9.8. Граница Infrastructure

`infrastructure/` содержит технические реализации системы.

К Infrastructure могут относиться:

- хранение данных;
- работа с базой данных;
- сеть;
- Browser API;
- внешние API;
- реализации шифрования;
- интеграции с устройством;
- техническое логирование;
- другие технические механизмы.

Infrastructure НЕ должен проникать внутрь Domain и навязывать ему технические детали.

При необходимости технические реализации должны предоставляться через соответствующие адаптеры, контракты или абстракции.

### 9.9. Граница Core

`core/` содержит наиболее стабильные, переиспользуемые и независимые от технологий примитивы и контракты, необходимые архитектуре.

Core должен оставаться максимально стабильным.

Core НЕ должен зависеть от:

- `presentation`;
- `application`;
- конкретных Domain-модулей;
- реализаций Infrastructure;
- реализаций Memory;
- реализации Design System.

Domain может зависеть от разрешённых стабильных абстракций и контрактов Core.

Core НЕ должен превращаться в место для размещения произвольного общего кода.

### 9.10. Граница Design System

`design/` является независимой Design System LifeGame.

```
design/
   ↓
presentation
```

Design НЕ должен зависеть от:

- Domain;
- Application;
- Infrastructure;
- Memory.

Domain и Application НЕ должны содержать визуальные решения.

Бизнес-логика НЕ должна знать о:

- цветах;
- типографике;
- отступах;
- радиусах;
- границах;
- тенях;
- градиентах;
- анимациях;
- визуальных темах;
- UI-компонентах.

Presentation использует Design System.

### 9.11. Взаимодействие между модулями

Независимые модули должны взаимодействовать через определённые контракты.

Прямой доступ к внутренней реализации другого модуля запрещён.

Предпочтительная схема:

```
Модуль A
   ↓
Контракт / Событие
   ↓
Граница системы
   ↓
Модуль B
```

Модуль должен предоставлять наружу только те данные и операции, которые действительно необходимы другим частям системы.

Внутренняя реализация модуля должна оставаться скрытой.

### 9.12. Граница безопасности

Безопасность является архитектурной частью LifeGame и НЕ должна рассматриваться только как техническая реализация.

Политика безопасности и техническая реализация безопасности должны быть разделены.

Принцип:

```
Политика безопасности
        ↓
Контракт безопасности
        ↓
Техническая реализация
```

Архитектура должна различать:

- правила безопасности;
- контроль доступа;
- аутентификацию;
- авторизацию;
- политику шифрования;
- реализацию шифрования;
- контроль целостности;
- аудит;
- технические механизмы защиты.

Конкретная техническая реализация безопасности НЕ должна становиться частью бизнес-логики.

### 9.13. Пользовательские и системные данные

Пользовательские и системные данные должны быть разделены логически и архитектурно.

```
DATA
│
├── USER DATA
│   ├── finance
│   ├── health
│   ├── development
│   └── profile
│
└── SYSTEM DATA
    ├── logs
    ├── audit
    ├── diagnostics
    ├── migrations
    └── system events
```

Они НЕ должны рассматриваться как единая неразделённая категория данных.

Архитектура должна позволять применять к ним различные:

- правила доступа;
- требования шифрования;
- сроки хранения;
- правила аудита;
- процедуры удаления;
- процедуры резервного копирования;
- процедуры миграции.

### 9.14. Domain Events и системное логирование

Domain НЕ должен напрямую записывать системные логи.

Запрещено:

```
domain
   ↓
system logger
```

Вместо этого используется:

```
domain
   ↓
Domain Event
   ↓
механизм событий
   ├── memory
   ├── audit
   └── diagnostics
```

Это сохраняет независимость бизнес-логики от системного логирования и диагностической инфраструктуры.

### 9.15. Внешние зависимости

Внешние библиотеки, SDK и API платформы НЕ должны напрямую проникать в Domain.

Например:

- SDK базы данных;
- HTTP-клиенты;
- Browser API;
- API платформы;
- сторонние библиотеки;
- SDK внешних сервисов.

Если внешняя технология необходима, она должна быть изолирована соответствующим адаптером, контрактом или границей Infrastructure.

Domain должен оставаться заменяемым независимо от конкретных внешних технологий.

### 9.16. Правила зависимостей обязательны

Каждый модуль должен иметь чётко определённые границы зависимостей.

Перед добавлением любого импорта необходимо ответить:

1. К какому уровню относится эта зависимость?
2. Зачем она необходима?
3. Направлена ли она внутрь архитектуры?
4. Не нарушает ли она изоляцию модулей?
5. Не переносит ли технические детали в Domain?
6. Не обходит ли существующий контракт?
7. Можно ли удалить эту зависимость без изменения бизнес-правил?

Если зависимость существует только потому, что так удобнее, она НЕ должна создаваться.

### 9.17. Архитектурное правило

> Работающий код НЕ считается корректным, если он нарушает архитектуру зависимостей.

Архитектура LifeGame должна сохранять:

- разделение ответственности;
- направление зависимостей внутрь;
- изоляцию Domain;
- независимость модулей;
- границы безопасности;
- разделение пользовательских и системных данных;
- заменяемость Infrastructure;
- возможность переноса на будущие платформы;
- тестируемость;
- сопровождаемость.

Любое изменение архитектурной границы должно быть осознанным, документированным и утверждённым ДО реализации.


## 2026-10-05 — Зафиксирована семантика Finance / Assets

Первый финансовый блок LifeGame концептуально называется **«Активы»**, а не «Ликвидные средства».

Активы — это имущество и финансовые средства пользователя, которые входят в его имущественную картину. В UI могут учитываться недвижимость (например, квартира), автомобиль, наличные, деньги на банковских счетах и картах, а также другие активы, которые пользователь обоснованно хочет включить в свой имущественный баланс.

### Архитектурное правило Assets

`domain/finance/assets/` хранит только сырые факты об активах: идентификатор, название и оценочную стоимость. Domain не хранит пользовательское состояние в постоянном хранилище и не обращается напрямую к Memory.

Историческое техническое название `liquid-funds` заменено на `assets` в текущем контракте Finance. Новые реализации не должны вводить сущности или UI, которые трактуют этот блок только как наличные деньги или деньги «доступные прямо сейчас».

**Важно:** актив не является автоматически ликвидностью. Наличие квартиры или автомобиля увеличивает имущественную стоимость пользователя, но не означает, что эти деньги доступны для немедленного покрытия расходов. Расчёты FSI должны отдельно определить, какие виды активов и с каким коэффициентом допустимо учитывать в показателе ликвидности.
