# LifeGame — Дневник тренировок 1.2

**Статус:** EXPERIMENTAL — доменная модель, каталог упражнений, жизненный цикл и Application orchestration; UI и постоянное хранилище не подключены.  
**Дата:** 10.10.2026

## 1. Цель и границы

Дневник тренировок — самостоятельный предметный модуль Health для фиксации фактически выполненной нагрузки и анализа прогресса. Это не медицинская карта и не источник автоматической диагностики. Версия задаёт контракт данных, стартовый каталог упражнений, допустимые переходы сессии и прикладные сценарии изменения существующей сессии. UI, Health Memory, БД и Apple Health не подключены.

## 2. Доменная модель

TrainingSession содержит идентификатор, календарную дату ISO YYYY-MM-DD, тип активности (strength/cardio/mobility/other), статус (planned/in_progress/completed), явно заданную интенсивность (light/moderate/vigorous/unknown), необязательные длительность и заметки, упражнения, дату создания и обновления.

Упражнение содержит идентификатор, название, явно заданные целевые группы мышц и подходы. Подход содержит повторения, явный статус выполнения и необязательное сопротивление. Сопротивление может иметь единицу kg/lb либо тип bodyweight/band/machine/other. Неизвестная масса не заменяется вымышленным весом.

## 3. Каталог упражнений

source/domain/training/exercise-catalog.js содержит стартовый неизменяемый каталог из 18 силовых упражнений. У каждого упражнения есть стабильный ID, русское и английское отображаемые название, нормализованные группы мышц и тип оборудования. Название можно локализовать или изменить без изменения ID. Каталог можно искать по ID, группе мышц, оборудованию и названию.

Канонические группы мышц: chest, back, shoulders, biceps, triceps, forearms, quadriceps, hamstrings, glutes, calves, core. Это текущий словарь для подготовки данных; он не является медицинской классификацией. Каталог — стартовый набор, а не полный перечень упражнений. Произвольные пользовательские упражнения, их жизненный цикл и хранение пока не реализованы.

## 4. Жизненный цикл сессии

source/domain/training/training-session-lifecycle.js реализует чистые доменные операции:
- startTrainingSession: только planned → in_progress.
- completeTrainingSession: только in_progress → completed; итоговая сущность повторно валидируется.
- reviseTrainingSession: исправление даты, типа активности, интенсивности, длительности, заметок и упражнений, включая исправление завершённой записи. ID, статус, createdAt, userId и неизвестные поля редактировать нельзя.

Каждая операция создаёт новую неизменяемую сущность, сохраняет ID и время создания, повторно валидирует данные и требует неубывающий updatedAt.

## 5. Application-сценарии

source/application/training/save-training-session.js отвечает за создание и первичное сохранение сессии через внедрённый repository.saveForUser(userId, session).

source/application/training/manage-training-session.js отвечает за изменение существующей сессии. Публичные операции:
- start({ userContext, sessionId });
- complete({ userContext, sessionId });
- revise({ userContext, sessionId, changes }).

Сценарий проверяет наличие контекста пользователя, загружает сессию через repository.findForUser(userId, sessionId), повторно валидирует загруженные данные доменной фабрикой, вызывает соответствующую Domain-операцию и сохраняет результат через repository.saveForUser(userId, session). Если запись не найдена в указанной области пользователя, возвращается ошибка TRAINING_SESSION_NOT_FOUND. Недопустимое изменение не сохраняется.

Контракт репозитория — абстракция, а не реализация безопасности. Конкретный адаптер обязан проверять актуальную серверную идентичность и владение записью на каждой операции. Нельзя считать клиентский userId доказательством авторизации. Для защиты от конкурентных обновлений адаптеру в дальнейшем потребуется атомарное условное сохранение по версии/updatedAt; такой механизм пока не реализован.

## 6. Проверка и границы архитектуры

Domain не знает о UI, Memory, Infrastructure, пользователях, БД, сети, Apple Health или криптографии. Application координирует сценарии через внедрённый репозиторий и часы; конкретная БД не подключена.

Новый агрегат не добавлен в текущий Health Memory. Не менялись текущий Health UI, общий Health Index и подготовка недельной силовой активности. Не реализованы постоянное хранение, шифрование, синхронизация web/Telegram/iOS, импорт Apple Health, программы тренировок, пользовательские упражнения и защита от конкурентных записей.

## 7. Безопасность и ограничения

Перед production-подключением требуется адаптер, который:
- связывает запрос с аутентифицированным серверным субъектом;
- проверяет владельца при чтении и записи;
- не доверяет userId из клиентского тела запроса;
- обеспечивает атомарность обновления;
- применяет утверждённую политику шифрования и минимизации данных;
- проверяется интеграционными тестами на попытки межпользовательского доступа.

Текущие Application-тесты проверяют передачу user scope и отсутствие записи при ошибках, но не доказывают безопасность несуществующего инфраструктурного адаптера.
