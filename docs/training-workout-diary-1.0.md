# LifeGame — Дневник тренировок 1.1

**Статус:** EXPERIMENTAL — доменная модель, каталог упражнений и переходы жизненного цикла; UI и постоянное хранилище не подключены.  
**Дата:** 10.10.2026

## 1. Цель и границы

Дневник тренировок — самостоятельный предметный модуль Health для фиксации фактически выполненной нагрузки и анализа прогресса. Это не медицинская карта и не источник автоматической диагностики. Версия задаёт контракт данных, стартовый каталог упражнений и допустимые переходы сессии. UI, Health Memory, БД и Apple Health не подключены.

## 2. Доменная модель

TrainingSession содержит идентификатор, календарную дату ISO YYYY-MM-DD, тип активности (strength/cardio/mobility/other), статус (planned/in_progress/completed), явно заданную интенсивность (light/moderate/vigorous/unknown), необязательные длительность и заметки, упражнения, дату создания и обновления.

Упражнение содержит идентификатор, название, явно заданные целевые группы мышц и подходы. Подход содержит повторения, явный статус выполнения и необязательное сопротивление. Сопротивление может иметь единицу kg/lb либо тип bodyweight/band/machine/other. Неизвестная масса не заменяется вымышленным весом.

## 3. Каталог упражнений

Файл source/domain/training/exercise-catalog.js содержит стартовый неизменяемый каталог из 18 силовых упражнений. У каждого упражнения есть стабильный ID, русское и английское отображаемые название, нормализованные группы мышц и тип оборудования. Название можно локализовать или изменить без изменения ID. Каталог можно искать по ID, группе мышц, оборудованию и названию.

Канонические группы мышц: chest, back, shoulders, biceps, triceps, forearms, quadriceps, hamstrings, glutes, calves, core. Это текущий словарь для подготовки данных; он не является медицинской классификацией. Каталог — стартовый набор, а не полный перечень упражнений. Произвольные пользовательские упражнения, их жизненный цикл и хранение пока не реализованы.

## 4. Жизненный цикл сессии

Файл source/domain/training/training-session-lifecycle.js реализует чистые доменные операции:

- startTrainingSession: разрешён только переход planned → in_progress.
- completeTrainingSession: разрешён только переход in_progress → completed; доменная фабрика повторно проверяет итоговую сессию.
- reviseTrainingSession: разрешает исправлять дату, тип активности, интенсивность, длительность, заметки и упражнения, включая исправления завершённой записи. ID, статус, createdAt, userId и неизвестные поля через эту операцию изменить нельзя.

Каждая операция создаёт новую неизменяемую сущность, сохраняет исходный ID и время создания, проверяет обновлённые данные и требует неубывающий updatedAt. Повторный старт, завершение из неправильного статуса и прямое изменение статуса через редактор отклоняются.

Переходы — доменные операции, а не сохранение: вызывающий Application-сценарий должен отдельно сохранять результат через авторизованный user-scoped repository. Реализация Application-сценариев start/complete/revise и постоянное хранение пока не добавлены.

## 5. Валидация

- Дата проверяется на существование, а не только по шаблону.
- Тип активности, статус и интенсивность должны быть явными.
- Каждый подход требует reps и completed; отсутствие не превращается в ноль или автоматически выполненный подход.
- Повторения и числовое сопротивление не могут быть отрицательными.
- Группы мышц задаются явно; дубликаты удаляются, порядок нормализуется.
- Завершённая силовая сессия должна содержать записи упражнений.
- Доменная сущность, каталог и вложенные структуры замораживаются после нормализации.

Модель не выводит интенсивность из веса, повторений, длительности или числа подходов. Квалификация силового дня выполняется отдельным контрактом; покрытие мышечных групп проверяется отдельно за неделю.

## 6. Границы Clean Architecture

**Domain — source/domain/training/:** чистая валидация, каталог и переходы жизненного цикла. Не знает о пользователях, UI, хранилищах, сети, Apple Health или криптографии; не выполняет побочных эффектов.

**Application — source/application/training/save-training-session.js:** проверяет контекст пользователя, получает идентификатор и время через внедрённые зависимости и вызывает контракт repository.saveForUser(userId, session). Не импортирует конкретную БД или Health Memory.

**Infrastructure — будущий адаптер:** обязан обеспечивать изоляцию по userId, серверную авторизацию и проверку прав при каждой операции. Клиентский userId сам по себе не доказывает право доступа. Хранилище, шифрование и политики доступа пока не реализованы.

**Presentation — будущий интерфейс:** вызывает Application use cases, не сохраняет данные напрямую и различает запланированные, выполняемые и завершённые сессии.

## 7. Пользовательские данные

userId намеренно не встроен в доменную сущность: принадлежность записи аккаунту — ответственность application/infrastructure boundary. Репозиторий принимает userId отдельно и обязан проверять доступ. Нельзя полагаться только на UI-фильтрацию или идентификатор, присланный клиентом.

Новый агрегат не добавлен в существующий in-memory Health Memory. Каталог и переходы не подключены к текущему Health UI или общему Health Index.

## 8. Не входит в версию 1.1

UI, пользовательские программы тренировок, пользовательский каталог упражнений, Application-сценарии изменения существующих записей, адаптер БД, миграции, шифрование, синхронизация web/Telegram/iOS, импорт Apple Health, автоматическая оценка интенсивности и подключение к общему Health Index.
