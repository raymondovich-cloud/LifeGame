# LifeGame — Контракт безопасного хранения дневника тренировок

**Статус:** PLANNED — архитектурный контракт; адаптер, схема БД и шифрование не реализованы.  
**Дата:** 10.10.2026

## 1. Цель и границы

Документ определяет требования к будущему persistence-адаптеру дневника тренировок. Он опирается на существующий Supabase/PostgreSQL контур LifeGame, но не изменяет миграции и не подключается к реальной базе.

Текущая реализация Domain/Application не является доказательством безопасности хранения. Существующие Health/Development адаптеры и их RLS — полезная отправная точка, но не готовая реализация дневника тренировок.

## 2. Предметная граница и размещение

- Domain: `source/domain/training/` — модель и правила жизненного цикла.
- Application: `source/application/training/` — сценарии и порты репозитория.
- Infrastructure: будущий адаптер в `source/infrastructure/supabase/`.
- Persistence: будущая миграция PostgreSQL в `supabase/migrations/`.
- Database security tests: `supabase/tests/database/` и соответствующие интеграционные тесты.

Не переносить SQL, Supabase SDK, RLS-детали или криптографические библиотеки в Domain. Не подключать UI к Supabase напрямую.

## 3. Предлагаемая модель хранения

Целевая таблица: `public.training_sessions`, одна запись на одну тренировочную сессию.

Минимальный набор технических полей:

- `id uuid primary key` — стабильный ID сессии;
- `user_id uuid not null references auth.users(id) on delete cascade` — владелец;
- `session_date date not null` — дата тренировки для календаря и выборок;
- `status text not null` — planned / in_progress / completed;
- `revision bigint not null` — монотонная версия для optimistic concurrency;
- `payload` — данные сессии, формат хранения определяется после утверждения модели шифрования;
- `created_at timestamptz not null`;
- `updated_at timestamptz not null`.

Это логическая спецификация, не готовый SQL. Перед миграцией нужно сопоставить поля с фактической моделью и определить, какие метаданные разрешено хранить в открытом виде. Доменный ID сейчас допускает произвольную строку; до реализации необходимо закрепить UUID как контракт ID либо добавить явное преобразование на границе Infrastructure.

Для календарных выборок нужен индекс по `(user_id, session_date)`; для списка по состоянию — только если подтверждён реальный сценарий запроса. Не добавлять индексы без подтверждённой потребности.

## 4. Авторизация и изоляция пользователя

Обязательные требования:

1. Владелец записи определяется серверной identity Supabase Auth, а не значением `userId`, переданным клиентом.
2. На таблице включается RLS; доступные клиентские операции ограничиваются ролью `authenticated`.
3. SELECT и DELETE используют ownership predicate, эквивалентный `(select auth.uid()) = user_id`.
4. INSERT требует `WITH CHECK ((select auth.uid()) = user_id)`.
5. UPDATE требует одновременно `USING ((select auth.uid()) = user_id)` и `WITH CHECK ((select auth.uid()) = user_id)`, чтобы пользователь не мог передать запись другому владельцу.
6. Табличные grants выдаются только для нужных операций; RLS не заменяется grants и grants не заменяют RLS.
7. Не выдавать доступ роли `anon`. Не использовать `service_role` или secret key в браузере, Telegram WebApp либо iOS-клиенте.
8. Нельзя добавлять обход RLS через `SECURITY DEFINER` без отдельного security review.
9. При отсутствии записи или недоступности чужой записи наружу возвращается единый результат «не найдено/недоступно», не раскрывающий существование записи другого пользователя.

Application use case может передавать user context как параметр порта, но это само по себе не является авторизацией. Supabase JWT должен проверяться сервером/БД, а политика доступа — действовать на каждой операции. Инфраструктурный адаптер обязан не подменять identity клиента произвольным userId.

## 5. Контракт репозитория

Текущий контракт `findForUser(userId, sessionId)` / `saveForUser(userId, session)` недостаточен для защиты от конкурентных обновлений и не должен считаться окончательным persistence API.

Целевой порт следует определить до реализации адаптера:

- `findForUser(userId, sessionId)` → `{ session, revision }` либо `null`;
- `insertForUser(userId, session)` → сохраняет новую запись без перезаписи существующей;
- `updateForUser(userId, session, expectedRevision)` → атомарно обновляет только при совпадении владельца и версии; возвращает новую revision;
- отсутствие совпадения revision → типизированная ошибка конфликта, без перезаписи последнего сохранённого состояния;
- удаление, если потребуется продуктом, должно быть отдельной операцией с той же ownership-проверкой и определённой политикой истории.

Application-сценарии необходимо обновить под этот порт до написания адаптера. Нельзя реализовывать конкурентную защиту последовательностью «прочитать → сравнить в JavaScript → безусловно записать»: проверка и обновление должны быть атомарны в БД. При конфликте интерфейс сможет предложить повторную загрузку/повторное применение изменений; автоматическое last-write-wins запрещено.

## 6. Защита от некорректных данных

- PostgreSQL constraints ограничивают обязательные поля и допустимые значения статуса.
- Domain повторно валидирует каждую загруженную сессию.
- JSON/payload проверяется по версии схемы и ограничивается по размеру.
- Сервер не принимает владельца, created_at или revision из пользовательского payload как доверенные значения.
- ID сессии не может быть переиспользован для перезаписи другой записи.
- Мутации, влияющие на статус, проходят только через утверждённые Application-сценарии и доменные переходы.
- Изменение завершённой сессии разрешено только в пределах Domain revise-контракта и должно увеличивать revision.

## 7. Шифрование и классификация данных

Текущая база содержит user-scoped таблицы и RLS, но это не доказывает наличие прикладного шифрования пользовательских данных. PostgreSQL/Supabase encryption-at-rest и TLS не следует описывать как end-to-end encryption.

Перед production-подключением необходимо отдельно утвердить threat model и key lifecycle. Минимальные требования:

- TLS для передачи данных и шифрование at rest на стороне провайдера;
- не хранить ключи шифрования рядом с шифротекстом и не помещать секреты в клиентский код или Git;
- определить, требуется ли application-layer encryption для заметок, упражнений, подходов и других чувствительных полей;
- определить создание, версионирование, ротацию, восстановление и отзыв ключей, включая вход с нескольких устройств;
- предусмотреть миграцию ключей и поведение при утрате доступа;
- исключить содержимое тренировок, токены и ключевой материал из логов, аналитики и диагностических сообщений.

Поскольку календарь требует выборок по дате, до реализации нужно явно решить, какие минимальные метаданные остаются открытыми для индексации, а какие шифруются. Это архитектурное решение не считается принятым этим документом. До утверждения модели шифрования нельзя заявлять, что пользовательские данные зашифрованы на уровне приложения или защищены сквозным шифрованием.

## 8. Удаление и жизненный цикл данных

- Удаление аккаунта должно иметь согласованную политику удаления тренировок через FK cascade или явно описанный процесс.
- Не добавлять резервные копии тренировок в логи или отдельные аналитические таблицы без отдельной цели и срока хранения.
- Аудит безопасности хранится отдельно от содержимого тренировки и не должен копировать notes, упражнения, веса или иные пользовательские значения.
- До запуска определить политику retention, backup/restore и проверку удаления из активного хранилища и резервных копий.

## 9. Обязательные проверки перед интеграцией

1. Пользователь A читает собственную сессию.
2. Пользователь A не может прочитать сессию пользователя B по известному ID.
3. Пользователь A не может обновить или удалить сессию пользователя B.
4. Попытка INSERT/UPDATE с чужим `user_id` отклоняется БД.
5. Нельзя сменить `user_id` существующей записи.
6. `anon` не может читать или изменять тренировочные записи.
7. Отсутствие JWT, просроченная/отозванная сессия и некорректный токен не дают доступ.
8. Два обновления одной revision: одно успешно, второе получает конфликт и не теряет данные.
9. Повторная вставка ID не перезаписывает существующую запись.
10. Ошибка репозитория не оставляет локальный cache в состоянии, которое выдаётся за сохранённое.
11. Запросы не возвращают данные между аккаунтами после выхода и смены пользователя.
12. Логи и ошибки не содержат пользовательский payload или секреты.

Проверки RLS и конкурентного доступа должны запускаться на реальной тестовой PostgreSQL/Supabase-среде. Unit-тесты с mock repository не доказывают изоляцию БД.

## 10. Решения, необходимые перед реализацией

- Зафиксировать UUID-контракт ID сессии.
- Выбрать точную форму payload и версионирование схемы.
- Утвердить границу открытых метаданных и application-layer encryption/key management.
- Уточнить порт репозитория для revision-based optimistic concurrency.
- Подготовить миграцию и интеграционные тесты, не затрагивая существующие Health/Development таблицы.
- Проверить migration SQL, RLS, grants, тесты и CI до подключения UI.

## 11. Статус

**PLANNED.** Это архитектурный контракт для следующего этапа. Таблица `training_sessions`, её миграция, persistence-адаптер, шифрование и тесты реальной БД не реализованы этим изменением.
